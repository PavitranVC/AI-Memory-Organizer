# Datasets

This project uses three kinds of data. Every user, conversation, message and memory that comes from a dataset is
labelled with a `dataset` field, so the kinds are never mixed (rule from `CLAUDE.md`):

| Label | Meaning | Used for | Loaded now |
|---|---|---|---|
| `benchmark` | A published benchmark with question-answer labels | Accuracy results (Stage 6) | **LoCoMo** |
| `real` | Conversations of real people | The project's own annotated dataset | Nothing yet (WildChat is planned) |
| `synthetic` | Generated by `scripts/datasets/generate-synthetic.js` | **Only** performance and scale numbers, never accuracy | On demand |
| *(no label)* | Created through the API (or `npm run seed`) | The app itself | |

Each loaded document also has `source: { name, id }`, the dataset's name and the **original id** inside it (for
example LoCoMo's `conv-26` or dialog id `D1:3`), so every row can be traced back to the source file.

Datasets are downloaded to `data/`, which is gitignored: the files are large and are not ours to redistribute.

## LoCoMo

**What it is.** Ten very long conversations between two people, each split into dated sessions (19 to 32
sessions per conversation), with question-answer labels for testing long-term conversational memory.

### How it maps to our schema

| LoCoMo | Our collection | Fields |
|---|---|---|
| one sample (`sample_id`, e.g. `conv-26`) | one **user** | `dataset: 'benchmark'`, `source: { name: 'locomo', id: 'conv-26' }`, email `locomo-conv-26@benchmark.invalid`, password = `SEED_PASSWORD` |
| one session (`session_N` + `session_N_date_time`) | one **conversation** | title `LoCoMo conv-26, session N`, `source.session = N`, `source.date` = the session time |
| one turn (`speaker`, `dia_id`, `text`) | one **message** | `speaker_a` → role `user`, `speaker_b` → role `assistant`; `source.id = dia_id`, `source.speaker` = the name; `sentAt` = session time + 1 second per turn (keeps the order) |
| an image turn (`blip_caption`) | the same message | the caption is appended: `... [shared an image: <caption>]` (the images are not released) |
| one `qa` entry | one **evalitem** | `question`, `answer`, `adversarialAnswer`, `category` (unchanged number), `questionType`, `evidence` (as written), `evidenceMessageIds` (matched messages), `unresolvedEvidence` |

Not loaded: `observation` and `session_summary` (generated by the authors with a model, not labels) and
`event_summary` (labels for a different task, event summarisation).

Each sample is written in **one transaction**, so a crash never leaves half a sample. Re-running the loader
skips samples that are loaded (found by the unique index on `source.name` + `source.id`); `--reset` deletes a
sample's user and everything that references it, then loads it again. The loader inserts directly and does
**not** queue extraction jobs: Stage 6 decides when and how memories are extracted.

### Question types

LoCoMo stores the category only as a number. We store that number unchanged and add a readable `questionType`.
The names follow the paper's five types; which number is which is **our reading of the data**, checked by
`npm run data:stats` (`results/stage5-dataset-stats.json`, "byCategory"):

| category | questionType | questions | Evidence for the name (from the stats run) |
|---|---|---|---|
| 1 | multi-hop | 282 | 98.2% cite more than one dialog turn |
| 2 | temporal | 321 | 76.6% start with "When" (other categories: 0 to 1.4%) |
| 3 | open-domain | 96 | Not separated by these checks (0% "When", 52.1% multi-turn evidence); the name is the remaining type |
| 4 | single-hop | 841 | 5.5% cite more than one turn |
| 5 | adversarial | 446 | 100% have an `adversarial_answer`; 99.6% have no `answer` |

| Sessions → conversations | 272 |
| Turns → messages | 5,882 (1,226 with an image caption) |

| Questions with no matched evidence at all | 4 |
| Load time (this cloud container, MongoDB 7 in Docker) | about 2.2 s |

The second run skipped all 10 samples (idempotent).

**Evidence clean-up.** A few evidence entries are malformed in the file. They are normalised, never guessed:
`"D8:6; D9:17"` is split into two ids, `"D:11:26"` becomes `D11:26`, `"D30:05"` becomes `D30:5`. Entries that still
do not match a turn (`"D"`, and two ids that point at turns that do not exist) are kept in `unresolvedEvidence`.
The original text always stays in `evidence`.

### Limitations

- **Small.** 10 conversations and 1,986 questions. Per-type results (only 96 open-domain questions) have wide
  confidence intervals.
- **Two people, not a person and an assistant.** We store `speaker_a` as `user` and `speaker_b` as `assistant`.
  The Stage 3 extractor only mines `user` messages, so facts stated by `speaker_b` are not extracted unless Stage 6
  changes that (for example by also extracting from the other speaker), while questions ask about both people.
- **How the conversations were made.** The LoCoMo paper describes the dialogues as machine-generated and then
  checked and edited by people. TODO: verify the exact procedure in the paper before writing about it.
- **No time zone.** Session times are read as UTC. Turns only have the session's time, so each turn is placed
  one second after the previous one; real gaps within a session are unknown.
- **Image captions are model-generated** (BLIP, according to the README), not human descriptions.
- **Non-commercial licence.** Fine for a university project; not for a product.

## Synthetic scale data

**What it is.** Memories generated by our own script, for the index and scale experiments in Stage 6 (10k / 100k
/ 1M memories). They are **never** used for accuracy, and every document has `dataset: 'synthetic'`.

```bash
npm run data:synthetic -- --memories 100000 --users 100 --seed 42 --reset
npm run data:synthetic -- --remove
```

How it imitates real data:
- Users: one per 1,000 memories by default (`--users` to change), named `Synthetic user N`, no password.
- Facts are chains of **versions**: 80% of facts have 1 version, 15% have 2 and 5% have 3. Each later version
  supersedes the earlier one exactly as `memoryService.updateMemory` does (`validTo` = next `validFrom`,
  `supersedes` / `supersededBy` links, `closedAt`). 3% of facts are deleted (current version retracted).
- Valid times between 2023 and 2025; recorded 0 to 2 days after the fact began. `_id`s carry the recorded time,
  so `_id` order follows insertion order, as with real data.
- Categories Learning, Personal, Health, Hobbies (created if missing); Health memories are `special`, others 15%
  `personal`; 90% Active; 0 to 3 tags; confidence 0.5 to 1.
- Content is built from short templates ("My sister is learning Spanish on weekends."). It is not meant to be
  realistic text, only realistic in size and shape.
- **Reproducible**: a seeded random generator (mulberry32), so the same `--seed` and sizes give identical documents,
  `_id`s included (tested).
- Inserted in batches straight through the driver (no per-document validation, for speed); the tests check that
  generated documents pass the `Memory` schema.

Runs so far (`results/stage5-synthetic-generate.txt`, cloud container, MongoDB 7 in Docker):

| Memories | Users | Current | Superseded | Retracted | Insert time |
|---|---|---|---|---|---|
| 10,000 | 10 | 7,725 | 2,020 | 255 | 0.7 s |
| 100,000 | 100 | 77,635 | 19,982 | 2,383 | 7.3 s |

The 1M run is left to the Stage 6 index benchmark.

Limitations: no conversations or messages are generated, so `sourceMessageIds` is empty (provenance cost is not
part of these numbers); template text makes the text index smaller than real text would; times measure this
machine only.
